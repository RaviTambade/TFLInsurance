# 🌱 Part 6 — Build the First Insurance Vertical Slice in ASP.NET Core

Now we are ready to write code. But I would tell the students:

> **"We are not going to build 20 controllers and 50 tables today."**
> **"We are going to make one business journey work end-to-end."**

Our first journey is:

```text
Customer
   ↓
Browse Insurance Product
   ↓
Create Proposal
   ↓
Submit Proposal
   ↓
LIC Staff Reviews
   ↓
Approve Proposal
   ↓
Issue Policy
```

This is called a **vertical slice**. It takes us from the UI/API all the way to the database.

# 2. Establish Dependencies

The dependency direction should be intentional.

```text
                Domain
               ↑     ↑
               │     │
        Application  │
               ↑     │
               │     │
        Infrastructure
               ↑
               │
              API
```

Or conceptually:

```text
API
 ↓
Application
 ↓
Domain

Infrastructure
 ↓
Domain
```

The important principle:

> **The Domain should not depend on Infrastructure.**

Your business rules should not know whether you use:

* MySQL
* SQL Server
* PostgreSQL
* MongoDB

That is an infrastructure concern.

# 6. Proposal Entity

Now we create the important business object.

```csharp
namespace LICInsurance.Domain.Entities;

public class Proposal
{
    public long ProposalId { get; set; }
    public string ProposalNumber { get; set; } = string.Empty;
    public long CustomerId { get; set; }
    public long? AgentId { get; set; }
    public long ProductId { get; set; }
    public decimal SumAssured { get; set; }
    public int PolicyTerm { get; set; }
    public decimal PremiumAmount { get; set; }
    public string PremiumFrequency { get; set; } = string.Empty;
    public string Status { get; private set; } = "Draft";
    public DateTime CreatedAt { get; set; }
    public DateTime? SubmittedAt { get; private set; }
    public DateTime? ApprovedAt { get; private set; }
    public DateTime? RejectedAt { get; private set; }

    public void Submit()
    {
        if (Status != "Draft")
            throw new InvalidOperationException(
                "Only a draft proposal can be submitted.");

        Status = "Submitted";
        SubmittedAt = DateTime.UtcNow;
    }

    public void Approve()
    {
        if (Status != "Submitted")
            throw new InvalidOperationException(
                "Only a submitted proposal can be approved.");

        Status = "Approved";
        ApprovedAt = DateTime.UtcNow;
    }

    public void Reject()
    {
        if (Status != "Submitted")
            throw new InvalidOperationException(
                "Only a submitted proposal can be rejected.");

        Status = "Rejected";
        RejectedAt = DateTime.UtcNow;
    }
}
```

## Stop here.

This is an important lesson. We didn't write:

```csharp
proposal.Status = "Approved";
```

from anywhere.

Instead:

```csharp
proposal.Approve();
```

Why?

Because:

> **State transitions belong to the domain.**

The entity protects its own lifecycle.

 

# 7. Domain Thinking vs CRUD Thinking

### CRUD approach

```csharp
proposal.Status = "Approved";
```

### Domain approach

```csharp
proposal.Approve();
```

The second approach communicates business intent. Imagine six months later someone asks:

> "Can a rejected proposal be approved?"

The answer should live in the domain model.

```csharp
if (Status != "Submitted")
    throw ...
```

That's a business rule.

# 9. Application Layer

Now we ask: "What can the application do?" We don't expose entities directly from our APIs. Instead, define DTOs.

## CreateProposalRequest

```csharp
namespace LICInsurance.Application.Proposals;

public class CreateProposalRequest
{
    public long CustomerId { get; set; }
    public long? AgentId { get; set; }
    public long ProductId { get; set; }
    public decimal SumAssured { get; set; }
    public int PolicyTerm { get; set; }
    public decimal PremiumAmount { get; set; }
    public string PremiumFrequency { get; set; } = string.Empty;
}
```

Why DTO?

Because:

> **Entity = domain representation.**
> **DTO = API contract.**

Do not couple your external API contract directly to your database model.



# 10. Proposal Service

Now we create the business use case.

```csharp
public interface IProposalService
{
    Task<ProposalResponse> CreateAsync( CreateProposalRequest request);
    Task SubmitAsync(long proposalId);
    Task ApproveAsync(long proposalId);
}
```

Notice the methods:

```text
Create
Submit
Approve
```

These are **business operations**.

Not:

```text
Update()
```

This is deliberate.



# 11. Implement Create Proposal

Conceptually:

```csharp
public async Task<ProposalResponse> CreateAsync(CreateProposalRequest request)
{
    var customer = await _customerRepository.GetByIdAsync(request.CustomerId);

    if (customer == null)
        throw new InvalidOperationException("Customer does not exist.");

    var product = await _productRepository.GetByIdAsync(request.ProductId);

    if (product == null)
        throw new InvalidOperationException("Insurance product does not exist.");

    if (product.Status != "Active")
        throw new InvalidOperationException("Insurance product is not active.");

    var proposal = new Proposal
    {
        ProposalNumber = GenerateProposalNumber(),
        CustomerId = request.CustomerId,
        AgentId = request.AgentId,
        ProductId = request.ProductId,
        SumAssured = request.SumAssured,
        PolicyTerm = request.PolicyTerm,
        PremiumAmount = request.PremiumAmount,
        PremiumFrequency = request.PremiumFrequency,
        CreatedAt = DateTime.UtcNow
    };

    await _proposalRepository.AddAsync(proposal);

    return MapToResponse(proposal);
}
```

The important thing isn't the syntax.

Look at the thought process:

```text
Customer exists?
       ↓
Product exists?
       ↓
Product active?
       ↓
Create proposal
       ↓
Persist
```

That's application engineering.


# 12. Submit Proposal

The API shouldn't simply execute:

```csharp
proposal.Status = "Submitted";
```

Instead:

```csharp
public async Task SubmitAsync(long proposalId)
{
    var proposal =await _proposalRepository.GetByIdAsync(proposalId);
    if (proposal == null)
        throw new KeyNotFoundException("Proposal not found.");
    proposal.Submit();
    await _proposalRepository.UpdateAsync(proposal);
}
```

The application orchestrates.
The domain validates.
The repository persists.
This separation is powerful.

# 14. API Controller

Now we expose the use cases.

```csharp
[ApiController]
[Route("api/proposals")]
public class ProposalsController : ControllerBase
{
    private readonly IProposalService _proposalService;

    public ProposalsController( IProposalService proposalService)
    {
        _proposalService = proposalService;
    }

    [HttpPost]
    public async Task<IActionResult> Create( CreateProposalRequest request)
    {
        var result = await _proposalService.CreateAsync(request);
        return Ok(result);
    }

    [HttpPost("{id}/submit")]
    public async Task<IActionResult> Submit(long id)
    {
        await _proposalService.SubmitAsync(id);
        return Ok();
    }

    [HttpPost("{id}/approve")]
    public async Task<IActionResult> Approve(long id)
    {
        await _proposalService.ApproveAsync(id);
        return Ok();
    }
}
```

Now our API communicates business intent:

```text
POST /api/proposals
POST /api/proposals/1001/submit
POST /api/proposals/1001/approve
```



# 15. Why This API Design Is Better

Compare:

### Weak

```http
PUT /api/proposals/1001
```

Request:

```json
{
  "status": "Approved"
}
```

The API says:

> "Change some data."

### Better

```http
POST /api/proposals/1001/approve
```

The API says:

> **"Perform the business operation: Approve Proposal."**

That is much easier to secure, audit, test and reason about.



# 16. Policy Issuance

Now comes our most interesting operation.

We have:

```text
Proposal
Status = Approved
```

The Policy Officer clicks:

> **Issue Policy**

Application service:

```csharp
public async Task<PolicyResponse> IssuePolicyAsync(
    long proposalId)
{
    var proposal =await _proposalRepository.GetByIdAsync(proposalId);

    if (proposal == null)
        throw new KeyNotFoundException("Proposal not found.");

    if (proposal.Status != "Approved")
        throw new InvalidOperationException("Only approved proposals can be issued.");
```

Then:

```csharp
    var policy = new Policy
    {
        PolicyNumber = GeneratePolicyNumber(),
        ProposalId = proposal.ProposalId,
        CustomerId = proposal.CustomerId,
        AgentId = proposal.AgentId,
        ProductId = proposal.ProductId,
        SumAssured = proposal.SumAssured,
        PremiumAmount = proposal.PremiumAmount,
        PremiumFrequency = proposal.PremiumFrequency,
        StartDate = DateTime.UtcNow.Date,

        MaturityDate =DateTime.UtcNow.Date.AddYears(proposal.PolicyTerm),
        Status = "Issued",
        IssuedAt = DateTime.UtcNow
    };

    await _policyRepository.AddAsync(policy);
    return MapToResponse(policy);
}
```

Now we have our first complete business chain:

```text
Customer
   ↓
Proposal
   ↓
Submit
   ↓
Underwriting
   ↓
Approve
   ↓
Issue Policy
```
 

# 17. But Something Is Missing

Suppose Policy is issued. Should the system stop there? No. Policy issuance may trigger:

```text
Policy Issued
     │
     ├── Generate Premium Schedule
     │
     ├── Generate Policy Document
     │
     ├── Notify Customer
     │
     ├── Notify Agent
     │
     └── Create Audit Log
```

Now we have discovered an important architectural concept:

# Domain Events

For example:

```text
PolicyIssuedEvent
```

The event could contain:

```csharp
public record PolicyIssuedEvent(
    long PolicyId,
    string PolicyNumber,
    long CustomerId);
```

Then handlers can perform additional work.

 

# 18. Why Events?

Imagine tomorrow LIC says: "Whenever a policy is issued, send an SMS, email, generate PDF, notify agent and update analytics." If all of that is inside:

```text
IssuePolicy()
```

the method becomes huge. Instead:

```text
Issue Policy
      ↓
PolicyIssuedEvent
      ↓
 ┌────┼────┬────┐
 ↓    ↓    ↓    ↓
Email SMS PDF Analytics
```

This gives us a path toward:

* RabbitMQ
* Kafka
* Azure Service Bus
* MassTransit
* Background processing

 

# 19. Transaction Thinking

There is another important question.

Suppose:

```text
Policy created ✅
Premium schedule failed ❌
```

- What should happen? 
- Should we leave the system in a partially completed state?

This is where developers learn:

* Database transactions
* Transaction boundaries
* Outbox pattern
* Idempotency
* Retry
* Eventual consistency

For the first version, we can keep policy creation and premium schedule creation in a database transaction. Later, for distributed systems, we can evolve toward:

```text
Transaction
    ↓
Outbox
    ↓
Message Broker
    ↓
Consumers
```

 
# 20. Testing the Business Rules

Now comes a very important Transflower principle: **"If a business rule is important, write a test for it."**

Example:

```text
Test:
Draft proposal can be submitted.
```

```text
Test:
Submitted proposal can be approved.
```

```text
Test:
Draft proposal cannot be approved.
```

```text
Test:
Rejected proposal cannot be approved.
```

```text
Test:
Only approved proposal can create policy.
```

These tests are more valuable than simply testing:

```text
GET /api/proposals
```

Why?

Because they protect the **business behavior**.
