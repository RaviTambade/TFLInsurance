**Ravi**

He approaches an LIC agent.


# 4. Now Introduce Underwriting

This is where application developers begin learning the real Insurance domain.

LIC cannot simply say:

> "Customer submitted proposal → Create policy."

The company needs to evaluate risk.

That process is called:

## Underwriting

The underwriter may evaluate:

* Age
* Income
* Occupation
* Existing policies
* Medical information
* Coverage amount
* Risk factors
* Documents

The proposal might move through:

```text
Submitted
    ↓
Under Review
    ↓
Risk Assessment
    ↓
Approved
```

Or:

```text
Submitted
    ↓
Under Review
    ↓
Rejected
```

Or perhaps:

```text
Submitted
    ↓
Additional Information Required
    ↓
Under Review
```

Now we have discovered our first major business rule:

> **A proposal must be approved before a policy can be issued.**

---

# 5. Convert Proposal Into Policy

Once approved:

```text
Proposal
   │
   │ Approved
   ↓
```

# 7. Policy Lifecycle

Let's model it.

```text
             Proposal
                │
                ↓
             Approved
                │
                ↓
          Policy Issued
                │
                ↓
              Active
                │
        ┌───────┴────────┐
        ↓                ↓
 Premium Due          Claim
        │                │
        ↓                ↓
 Premium Paid       Claim Process
        │                │
        ↓                ↓
    Renewed          Settlement
        │
        ↓
      Active
```

There can also be:

```text
Active
  ↓
Lapsed
  ↓
Revived
  ↓
Active
```

and:

```text
Active
  ↓
Matured
```

This is where we introduce:

# State Machine

The policy has a **state**.

For example:

```text
PolicyStatus

Draft
Submitted
Approved
Issued
Active
Lapsed
Revived
Matured
Cancelled
```

Not every transition should be allowed.

For example:

```text
Draft → Submitted       ✅
Submitted → Approved    ✅
Approved → Issued       ✅
Issued → Active         ✅

Draft → Matured         ❌
Cancelled → Active      ❌
```

This becomes a **business rule**, not merely a programming condition.

# 14. From Modules to Microservices?

Here I would stop the students.

I would say:

> "Don't create 15 microservices just because we identified 15 modules."

Start with a **modular monolith**.

For example:

```text
LIC Insurance Application
│
└── ASP.NET Core
     │
     ├── Customer Module
     ├── Agent Module
     ├── Policy Module
     ├── Premium Module
     ├── Claim Module
     ├── Payment Module
     └── Notification Module
```

Keep clear boundaries.

Later, if scale or organizational needs justify it, selected modules can become services.

This teaches an important engineering principle:

> **Architecture should emerge from business boundaries and operational needs—not from fashion.**

# 18. Then Introduce Events

Something interesting happens when a policy is issued.

We might need to:

* Generate policy document
* Send email
* Send SMS
* Update dashboard
* Create premium schedule
* Notify agent
* Record audit event

Instead of making the policy API synchronously do everything:

```text
Policy Issued
     │
     ├── Generate Document
     ├── Send Email
     ├── Send SMS
     ├── Create Premium Schedule
     └── Notify Agent
```

We can introduce:

```text
PolicyIssuedEvent
```

and an event-driven architecture.

Now students are naturally learning:

* Events
* Message queues
* Kafka
* RabbitMQ
* Background processing
* Eventually consistent workflows
