# 🌱 Part 10 — LIC Staff Portal: From CRUD to Business Workflow

Now we enter the **heart of the insurance organization**.

Until now, we have looked at the system from the perspective of:

* Customer
* Agent

Now we ask:

> **"What happens after the customer or agent submits a proposal?"**

This is where LIC staff enters the picture.

---

# 1. Meet the LIC Staff

Don't model every employee as simply:

```text
User
Role
```

Start understanding their **business responsibility**.

```text
LIC Staff
   │
   ├── Policy Officer
   │      └── Policy processing
   │
   ├── Underwriter
   │      └── Risk evaluation
   │

   │      └── Claim assessment
   │
```

The software should reflect these responsibilities.

# 4. Work Queue

This is an important enterprise concept.

A staff member shouldn't receive:

```text
10,00,000 proposals
```

and manually find work.

Instead:

```text
Proposal
    ↓
Business Rules
    ↓
Assignment
    ↓
Work Queue
```

Example:

```text
Underwriting Queue
--------------------------
PROP1001
PROP1005
PROP1011
PROP1019
```

A queue item might contain:

```text
WorkItemId
ReferenceId
WorkType
AssignedTo
Priority
Status
CreatedAt
DueAt
```

# 8. Risk Is Not Approval

This distinction is important.

Suppose the system calculates:

```text
Risk Score = 72
```

That does not necessarily mean:

```text
Approved
```

Instead:

```text
Risk Score
    ↓
Risk Category
    ↓
Underwriting Rules
    ↓
Human Review
    ↓
Decision
```

For example:

```text
0 - 30     Low
31 - 60    Medium
61 - 80    High
81 - 100   Very High
```

These numbers are only illustrative; actual insurance rules must come from the business.

# 13. Approval Authority

Now ask:

> Can every underwriter approve every policy?

Probably not.

Imagine:

```text
Underwriter
   ↓
Approval Limit = ₹50 Lakh
```

Proposal:

```text
₹25 Lakh
```

Can approve.

But:

```text
₹2 Crore
```

may require:

```text
Senior Officer
      ↓
Manager
```

So our business rule becomes:

```text
Sum Assured
      ↓
Approval Authority
```

Example:

```text
< ₹50 Lakh
   ↓
Underwriter

₹50 Lakh - ₹1 Crore
   ↓
Senior Underwriter

> ₹1 Crore
   ↓
Manager
```

Again, these are illustrative rules.

# 15. Approval

Suppose everything is valid.

Underwriter clicks:

```text
Approve
```

Our application service executes:

```csharp
public async Task ApproveProposalAsync(
    long proposalId,
    long employeeId)
{
    var proposal =
        await _proposalRepository
            .GetByIdAsync(proposalId);

    if (proposal == null)
        throw new KeyNotFoundException();

    await _authorizationService
        .ValidateApprovalAuthorityAsync(
            employeeId,
            proposal);

    proposal.Approve();

    await _proposalRepository
        .UpdateAsync(proposal);

    await _eventPublisher.PublishAsync(
        new ProposalApprovedEvent(
            proposal.ProposalId));
}
```

Now we have:

```text
Authorization
      ↓
Domain Rule
      ↓
Persistence
      ↓
Event
```

# 17. Premium Schedule

A policy isn't just:

```text
PolicyNumber
SumAssured
Premium
```

It can have a payment schedule.

Example:

```text
Policy: LIC100001

Premium Frequency: Yearly

2026-09-15    ₹18,500    Due
2027-09-15    ₹18,500    Scheduled
2028-09-15    ₹18,500    Scheduled
2029-09-15    ₹18,500    Scheduled
...
```

So we introduce:

```text
Policy
   │
   └── PremiumSchedule
            │
            ├── Premium 1
            ├── Premium 2
            ├── Premium 3
            └── ...
```

Database:

```sql
CREATE TABLE premium_schedules
(
    premium_schedule_id BIGINT AUTO_INCREMENT PRIMARY KEY,

    policy_id BIGINT NOT NULL,

    installment_number INT NOT NULL,

    due_date DATE NOT NULL,

    amount DECIMAL(18,2) NOT NULL,

    status VARCHAR(30) NOT NULL,

    paid_date DATE NULL,

    FOREIGN KEY (policy_id)
        REFERENCES policies(policy_id)
);
```

# 18. Payment

Now the Accounts Officer becomes important.

Customer sees:

```text
Premium Due

Policy: LIC100001
Amount: ₹18,500

[ Pay Now ]
```

The payment flow:

```text
Customer
   ↓
Payment Gateway
   ↓
Payment Result
   ↓
Payment API
   ↓
Verify Transaction
   ↓
Premium Schedule
   ↓
Mark Paid
   ↓
Receipt
```

Important:

> **Never trust the browser's statement that payment succeeded.**

The backend must verify the payment with the payment provider according to the provider's integration model.

# 19. Payment and Policy Are Different Concepts

A common beginner mistake:

```text
Policy.PremiumPaid = true
```

This becomes inadequate very quickly.

Instead:

```text
Policy
   ↓
PremiumSchedule
   ↓
PaymentTransaction
   ↓
Receipt
```

Now we can answer:

> Which installment?

> When was it paid?

> Which transaction?

> What was the gateway response?

> Was it refunded?

> Was it reversed?

This is domain modeling.

# 🚀 Part 11 — Claims Management

Now we enter one of the most important Insurance domains:

# **Claims**

The customer has a policy.

Something happens.

The customer says:

> **"I want to claim my insurance benefit."**

Now the system must understand:

```text
Policy
   ↓
Claim
   ↓
Claim Type
   ↓
Documents
   ↓
Eligibility
   ↓
Assessment
   ↓
Approval / Rejection
   ↓
Settlement
   ↓
Payment
```

And this introduces completely new concepts:

**Claim lifecycle → Claim investigation → Claim reserve → Claim assessment → Fraud detection → Approval authority → Settlement → Payment → Audit**

This is where we will take the application from **Policy Management** into a complete **Insurance Management System**.
