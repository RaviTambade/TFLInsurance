# 🌱 Part 7 — Authentication, Authorization and Role-Based Insurance Portals

Now our database and first business workflow are ready.

I would tell the developers:

> **"We have built the Insurance engine. Now let's decide who is allowed to drive which part of it."**

In an Insurance application, **security is not an add-on**.

A customer, agent, claims officer and administrator may all call the same backend, but they must not have the same capabilities.

---

# 1. Authentication vs Authorization

Start with these two concepts.

### Authentication

> **Who are you?**

Example:

```text
Ravi
    ↓
Username + Password
    ↓
Identity verification
    ↓
JWT Token
```

### Authorization

> **What are you allowed to do?**

Example:

```text
Ravi
Role = Customer

Can:
   View own policies       ✅
   Pay own premium         ✅
   Raise own claim        ✅

Cannot:
   Approve proposal       ❌
   Approve claim          ❌
   Issue policy           ❌
   View all customers     ❌
```

This distinction is fundamental.

# 3. JWT Authentication

For our ASP.NET Core application:

```text
Login
  ↓
Identity verification
  ↓
JWT generated
  ↓
Client stores token
  ↓
Token sent with API request
```

Example:

```http
Authorization: Bearer eyJhbGciOi...
```

The token can contain claims such as:

```json
{
  "sub": "1001",
  "name": "Ravi",
  "role": "Customer"
}
```

For an agent:

```json
{
  "sub": "2001",
  "name": "Agent Kumar",
  "role": "Agent"
}
```

---

# 4. Configure JWT in ASP.NET Core

In `Program.cs`:

```csharp
builder.Services
    .AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options =>
    {
        options.TokenValidationParameters =
            new TokenValidationParameters
            {
                ValidateIssuer = true,
                ValidateAudience = true,
                ValidateLifetime = true,
                ValidateIssuerSigningKey = true,

                ValidIssuer =
                    builder.Configuration["Jwt:Issuer"],

                ValidAudience =
                    builder.Configuration["Jwt:Audience"],

                IssuerSigningKey =
                    new SymmetricSecurityKey(
                        Encoding.UTF8.GetBytes(
                            builder.Configuration["Jwt:Key"]!))
            };
    });
```

Then:

```csharp
builder.Services.AddAuthorization();
```

And middleware:

```csharp
app.UseAuthentication();

app.UseAuthorization();
```

Order matters.

```text
Request
  ↓
Authentication
  ↓
Authorization
  ↓
Controller
```

# 5. Customer API

Suppose we have:

```http
GET /api/customers/me
```

We don't want:

```text
Customer A
```

to retrieve:

```text
Customer B
```

by changing the ID in the URL.

Instead:

```csharp
[Authorize(Roles = "Customer")]
[HttpGet("me")]
public async Task<IActionResult> GetMyProfile()
{
    var userId = User.FindFirstValue(
        ClaimTypes.NameIdentifier);

    var customer =
        await _customerService
            .GetByUserIdAsync(long.Parse(userId!));

    return Ok(customer);
}
```

The important concept:

> **Never trust an ID supplied by the client to determine ownership.**

The authenticated identity should determine the customer context.

---

# 6. Agent API

Now consider:

```http
GET /api/agents/my-customers
```

An agent should see only customers assigned to that agent.

```csharp
[Authorize(Roles = "Agent")]
[HttpGet("my-customers")]
public async Task<IActionResult> GetMyCustomers()
{
    var userId =
        User.FindFirstValue(
            ClaimTypes.NameIdentifier);

    var customers =
        await _agentService
            .GetCustomersAsync(long.Parse(userId!));

    return Ok(customers);
}
```

Business rule:

```text
Agent
  ↓
Only assigned customers
```

Not:

```text
Agent
  ↓
All LIC customers
```

# 7. Policy Officer API

Now:

```http
POST /api/proposals/1001/approve
```

This operation should be protected.

```csharp
[Authorize(Roles = "PolicyOfficer,Manager,Admin")]
[HttpPost("{id}/approve")]
public async Task<IActionResult> Approve(long id)
{
    await _proposalService.ApproveAsync(id);

    return Ok();
}
```

Now the security boundary is explicit.

---

# 8. Claims Officer

Similarly:

```csharp
[Authorize(Roles = "ClaimsOfficer,Manager,Admin")]
[HttpPost("{id}/approve")]
public async Task<IActionResult> ApproveClaim(long id)
{
    await _claimService.ApproveAsync(id);

    return Ok();
}
```

This is much better than:

```csharp
if (user.Role == "ClaimsOfficer")
```

scattered throughout controllers.

Use the framework's authorization model.

# 9. But Role Is Not Always Enough

Here is where enterprise applications become interesting.

Suppose:

```text
Agent A
```

has:

```text
Customer 101
Customer 102
Customer 103
```

and requests:

```http
GET /api/customers/999
```

The user has a valid:

```text
Role = Agent
```

but should still receive:

```text
403 Forbidden
```

because Customer 999 doesn't belong to that agent.

So we need two levels:

```text
Role Authorization
        +
Resource Authorization
```

In simple language:

> **"Are you an Agent?"**
>
> and
>
> **"Are you allowed to access THIS customer's data?"**

# 10. Customer Data Isolation

This becomes especially important for policies.

Customer Ravi:

```text
GET /api/policies/10001
```

should not allow him to see:

```text
Policy 10002
```

belonging to another customer.

The service should verify:

```text
Authenticated User
       ↓
Customer
       ↓
Policy.CustomerId
```

Only if they match:

```text
Allow
```

Otherwise:

```text
Forbidden
```

---

# 11. Don't Put Authorization Only in the UI

This is a classic mistake.

A developer hides the button:

```text
Approve Proposal
```

from customers.

They think the feature is secure.

It isn't.

A customer could directly call:

```http
POST /api/proposals/1001/approve
```

using Postman.

Therefore:

```text
UI Security
     ≠
API Security
```

The backend must enforce authorization.

# 14. Introduce CQRS

Don't rush into implementing CQRS everywhere.

First understand the problem.

A customer asks:

> "Show my policy."

That's a **query**.

A Policy Officer says:

> "Approve proposal."

That's a **command**.

So:

```text
Query
 ↓
Read information
```

and:

```text
Command
 ↓
Change business state
```

This gives us:

```text
                 Application
                      │
             ┌────────┴────────┐
             ↓                 ↓
          Queries           Commands
             ↓                 ↓
       Read operations     State changes
```

For example:

```text
GET /api/policies/1001
```

is a query.

```text
POST /api/proposals/1001/approve
```

is a command.

This distinction becomes especially valuable as the system grows.

# 16. Add Refresh Tokens

JWT access tokens should generally be short-lived.

Conceptually:

```text
Login
 ↓
Access Token
 ↓
Short lifetime
 ↓
Expires
```

Rather than forcing the user to log in every time:

```text
Refresh Token
 ↓
Request new Access Token
```

The flow:

```text
             Login
               ↓
       Access + Refresh Token
               ↓
       ┌───────┴────────┐
       ↓                ↓
 Access Token       Refresh Token
       ↓                ↓
 API Calls          Token Renewal
```

Refresh tokens should be handled carefully:

* Store securely
* Rotate where appropriate
* Revoke when necessary
* Never treat them like ordinary access tokens
