# 🌱 Part 9 — Build the Agent Portal

Now we introduce our second major persona:  **The LIC Agent** As a Transflower Mentor, I would tell developers:  **"A Customer uses the Insurance system for themselves. An Agent uses the system to serve many customers."** That one difference changes the application design.

A Customer thinks:

```text
My Policy
My Premium
My Claim
```

An Agent thinks:

```text
My Customers
Their Proposals
Their Policies
Their Premiums
My Commission
```

So let's model the Agent journey.

# 3. Agent Customer Relationship

We previously created:

```text
Agent
Customer
```

But we haven't explicitly modeled the relationship.

Ask the students:
- Can one customer have multiple agents?
- Can one agent have hundreds of customers?
- Can an agent's relationship with a customer have a start/end date?

These are **business questions**. For our first version, assume:

```text
One Customer
      ↓
One Primary Agent

One Agent
      ↓
Many Customers
```

We can add:

```sql id="g5e5n4"
ALTER TABLE customers
ADD COLUMN agent_id BIGINT NULL;
```

Then:

```sql id="qu70uc"
ALTER TABLE customers
ADD CONSTRAINT fk_customer_agent
FOREIGN KEY (agent_id)
REFERENCES agents(agent_id);
```

Now:

```text
Agent 1 ───────── * Customer
```

 

# 4. But Don't Stop There

Enterprise developers should ask:  What happens if the customer changes agents? If we simply overwrite:

```text id="6pny8n"
customer.agent_id
```

we lose history.

Maybe the business needs:

```text
Customer Ravi

2024 → Agent A
2025 → Agent B
2026 → Agent C
```

Then we need a relationship/history table.

```sql id="t7y5mi"
CREATE TABLE customer_agent_assignments (
    assignment_id BIGINT AUTO_INCREMENT PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    agent_id BIGINT NOT NULL,
    start_date DATE NOT NULL,
    end_date DATE NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'Active', 
    FOREIGN KEY (customer_id) REFERENCES customers(customer_id),
    FOREIGN KEY (agent_id)    REFERENCES agents(agent_id)
);
```

Now we can represent history.

```text
Customer
   │
   └── CustomerAgentAssignment
            │
            ├── Agent A
            ├── Agent B
            └── Agent C
```

This is a good example of why: **Database design must follow business history, not just today's screen.**

 

# 5. Agent → Customer Authorization

Now imagine Agent Kumar has:

```text
Customer 101
Customer 102
Customer 103
```

He requests:

```http
GET /api/customers/999
```

Customer 999 belongs to Agent Priya.

What should happen?

```text
403 Forbidden
```

Even though:

```text
Kumar
Role = Agent
```

he does not have access to this resource. So our authorization has two dimensions:

```text
                 Authorization
                      │
            ┌─────────┴─────────┐
            ↓                   ↓
       Role-based          Resource-based
            │                   │
       Is Agent?        Is customer assigned?
```

This is a very important enterprise security concept.

 

# 6. Agent Customer API

Instead of allowing an agent to query everything:

```http
GET /api/customers
```

we expose:

```http
GET /api/agents/me/customers
```

The backend derives the agent from the authenticated identity.

```csharp id="d7fn4f"
[Authorize(Roles = "Agent")]
[HttpGet("me/customers")]
public async Task<IActionResult> GetMyCustomers()
{
    var userId = User.FindFirstValue( ClaimTypes.NameIdentifier);
    var customers = await _agentService.GetAssignedCustomersAsync(long.Parse(userId!));
    return Ok(customers);
}
```

Notice:

The frontend doesn't send:

```json id="2g3z1s"
{
    "agentId": 123
}
```

The server knows who the agent is from the authenticated identity.

# 8. Agent Creates Proposal on Behalf of Customer

This is different from the Customer Portal.

Customer:

```text
POST /api/proposals
```

Agent:

```text
POST /api/agents/proposals
```

Request:

```json id="h2f2xj"
{
  "customerId": 1001,
  "productId": 1,
  "sumAssured": 1000000,
  "policyTerm": 20,
  "premiumFrequency": "Yearly"
}
```

But the backend must verify:

```text
Agent authenticated?
       ↓
Customer exists?
       ↓
Customer assigned to agent?
       ↓
Product active?
       ↓
Customer eligible?
       ↓
Create proposal
```

The critical rule is: **An Agent cannot create a proposal for an arbitrary customer.**

    CreateProposalForCustomerAsync(
        long agentUserId,
        CreateProposalRequest request)
{
    var agent =
        await _agentRepository
            .GetByUserIdAsync(agentUserId);

    if (agent == null)
        throw new UnauthorizedAccessException();

        await _customerRepository
            .GetByIdAsync(request.CustomerId);

# 11. Agent Commission

Now we reach another important Insurance domain concept. An agent may receive commission based on:

* Product
* Premium
* Policy type
* Policy year
* Commission rules
* Business period

Don't simply put:

```text
commission = premium * 10%
```

inside the controller.

That's a business rule.

Create a domain concept.

```text id="i5z15j"
Commission Rule
       │
       ├── Product
       ├── Rate
       ├── Effective From
       └── Effective To
```

Database:

```sql id="t4xvyn"
CREATE TABLE commission_rules (
    commission_rule_id BIGINT AUTO_INCREMENT PRIMARY KEY,
    product_id BIGINT NOT NULL,
    commission_rate DECIMAL(8,4) NOT NULL,
    effective_from DATE NOT NULL,
    effective_to DATE NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'Active',
    FOREIGN KEY (product_id) REFERENCES insurance_products(product_id)
);
```


# 12. Agent Commission

Then:

```sql id="gk1t3p"
CREATE TABLE agent_commissions (
    commission_id BIGINT AUTO_INCREMENT PRIMARY KEY,
    agent_id BIGINT NOT NULL,
    policy_id BIGINT NOT NULL,
    commission_rule_id BIGINT NOT NULL,
    premium_amount DECIMAL(18,2) NOT NULL,
    commission_rate DECIMAL(8,4) NOT NULL,
    commission_amount DECIMAL(18,2) NOT NULL,
    status VARCHAR(30) NOT NULL DEFAULT 'Pending',
    calculated_at DATETIME NOT NULL  DEFAULT CURRENT_TIMESTAMP,
    paid_at DATETIME NULL,

    FOREIGN KEY (agent_id) REFERENCES agents(agent_id),
    FOREIGN KEY (policy_id) REFERENCES policies(policy_id),
    FOREIGN KEY (commission_rule_id) REFERENCES commission_rules(commission_rule_id)
);
```

Now we have history. Suppose the commission rate changes:

```text
2025 → 8%
2026 → 10%
```

Old policies should not suddenly change to 10%. That's why we store the actual rate used:

```text
commission_rate
```

and the rule:

```text
commission_rule_id
```

This is **historical data modeling**.

# 🌱 Mentor Lesson

I would stop here and ask students one question:  **"What is an Agent?"** A beginner might say:  "An Agent is a user with role = Agent." That's technically true. But it is not domain understanding. A better answer is:  **"An Agent is a business actor who represents the insurance company in serving assigned customers, creating and tracking proposals, assisting with policies and claims, and earning commission according to applicable business rules."** That's the difference between:

```text
Software Developer
```

and

```text
Domain-aware Application Developer
```
