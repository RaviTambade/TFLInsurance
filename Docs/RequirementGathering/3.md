# 9. Business Rules

For example:

### Rule 1

A proposal cannot be submitted without required information.

```text
Customer ✓
Product ✓
Term ✓
Sum Assured ✓
Nominee ✓
Documents ✓
```

### Rule 2 

Only a submitted proposal can enter underwriting.

### Rule 3

Only an authorized employee can approve a proposal.

### Rule 4

Only an approved proposal can become a policy.

### Rule 5

A rejected proposal cannot directly become an active policy. These rules are more important than the database table.

# 17. But Don't Make This Mistake

A beginner may create:

```text
POST /api/policies
```

and allow anyone to create a policy. That's wrong. Policy creation is a **business operation**, not merely CRUD. A better workflow is:

```text
POST /api/proposals
       ↓
POST /api/proposals/{id}/submit
       ↓
POST /api/proposals/{id}/approve
       ↓
POST /api/policies
```

Or even better, policy issuance can be an explicit domain operation:

```text
POST /api/proposals/{id}/issue-policy
```

The API should communicate **business intent**.
