# 🌱 Part 4 — Designing the LIC Insurance Database

Now we move one step closer to implementation.

I would tell the developers:

> **"We have understood the business. We have identified the actors and use cases. Now let's design the data that the business needs."**
>
> But remember:
>
> **Database design is not table design. It is business modeling expressed through data.**

Our fictional customer is **LIC**, and our application serves:

* Customers
* Agents
* LIC Staff
* Managers
* Policy Officers
* Claims Officers
* Accounts Officers

# 2. Identity Model

First, users need to authenticate.

Instead of putting login information directly inside Customer, Agent and Employee tables, separate **identity** from **business profile**.

```text
Users
Roles
UserRoles
```

Example:

```text
User
-----
UserId
Username
Email
PasswordHash
Status
CreatedAt
```

Role:

```text
Role
----
RoleId
RoleName
```

Roles could be:

```text
Admin
Manager
Agent
Customer
PolicyOfficer
ClaimsOfficer
AccountsOfficer
```

Then:

```text
UserRole
--------
UserId
RoleId
```

Why separate them?

Because:

> **Authentication answers "Who are you?"**
>
> **Authorization answers "What are you allowed to do?"**



But here we should pause.

Instead of simply storing:



# 11. Payment

Now distinguish **Premium** from **Payment**.

Premium:

> "Ravi owes ₹25,000."

Payment:

> "Ravi paid ₹25,000."

So:

```text
Payment
-------
PaymentId
PremiumId
PolicyId
TransactionReference
Amount
PaymentMethod
PaymentDate
Status
GatewayResponse
CreatedAt
```

Relationship:

```text
Premium
   │
   └── Payment
```

We should also consider payment retries.

For example:

```text
Payment Attempt 1 → Failed
Payment Attempt 2 → Failed
Payment Attempt 3 → Success
```

So an enterprise system might eventually introduce:

```text
PaymentTransaction
PaymentAttempt
```

instead of assuming one premium always has one payment.

# 12. Claim

Now the most important business workflow.

```text

-----

ClaimantId
ClaimType
ClaimAmount
Status
RaisedAt
ApprovedAt
RejectedAt
SettledAt
```

Relationship:

```text
Policy 1 ───── * Claim
```

Why `*`?

Because depending on the domain, a policy may have multiple claim-related transactions over its lifetime.

The exact cardinality must be confirmed with the business.

That's an important lesson:

> **Never assume relationships. Ask the domain expert.**

# 17. Database Does Not Define the Business

Here is a common developer mistake.

They create:

```text
PolicyStatus VARCHAR(50)
```

and then anyone can put:

```text
"ABC"
"XYZ"
"Done"
"Whatever"
```

Instead, the domain should define valid states.

For example:

```text
Draft
Submitted
UnderReview
Approved
Issued
Active
Lapsed
Revived
Matured
Cancelled
```

And valid transitions should be controlled by application/business logic.

# 20. Indexing

Now I ask the developers:

> "Suppose LIC has 50 million policies. Can we simply run SELECT queries everywhere?"

No.

We need indexes based on actual access patterns.

Likely candidates:

```text
Customer.CustomerNumber
Customer.Email

Agent.AgentCode
Agent.LicenseNumber

Proposal.ProposalNumber
Proposal.CustomerId
Proposal.AgentId
Proposal.Status

Policy.PolicyNumber
Policy.CustomerId
Policy.AgentId
Policy.Status

Premium.PolicyId
Premium.DueDate
Premium.Status

Payment.TransactionReference

Claim.ClaimNumber
Claim.PolicyId
Claim.Status
```

But remember:

> **Don't index everything.**

Indexes improve reads but add:

* Storage
* Write cost
* Maintenance overhead

Design indexes from **query patterns**.

# 21. Now Think Like a Production Engineer

Suppose a customer presses:

**Pay Premium**

twice.

What happens?

Without protection:

```text
Click 1 → ₹25,000
Click 2 → ₹25,000
```

Customer may accidentally pay twice.

Therefore, financial systems need **idempotency**.

For example:

```text
IdempotencyKey = ABC123
```

The server can ensure:

```text
ABC123 → One successful business operation
```

This is where our Insurance application starts teaching serious distributed-system concepts.

# 🌱 The Transflower Mentor Rule

And I would finish today's session with this:

> **Don't ask "Which table should I create?"**
>
> Ask:
>
> **"What business problem am I modeling?"**
>
> Don't ask:
>

>
> **"Which business capability am I exposing?"**

>
