# 🌱 Part 8 — Build the Customer Portal

Now we move from **backend engineering** to **user experience**. I would tell the developers:  **"Don't start by creating screens. Start by understanding the customer's journey."** Our customer is not thinking:  "I want to call the ProposalController." The customer is thinking:  **"I want to buy insurance, understand my premium, submit my documents, and know what is happening with my application."** That difference is the beginning of good application development.

# 4. Authentication Service

Angular service:

```typescript
@Injectable({ providedIn: 'root' })
export class AuthService { 
    
  private apiUrl = 'https://localhost:7001/api/auth';

  constructor(private http: HttpClient) {}

  login(request: LoginRequest) {
    return this.http.post<LoginResponse>( `${this.apiUrl}/login`,  request );
  }

  logout() {  localStorage.removeItem('accessToken');  }

  getToken(): string | null { return localStorage.getItem('accessToken');
  }
}
```

For a production application, consider stronger browser storage/security patterns rather than blindly placing long-lived tokens in `localStorage`.

 

# 5. HTTP Interceptor

We don't want developers to manually write:

```http
Authorization: Bearer ...
```

for every request.

Create an interceptor.

```typescript
export const authInterceptor: HttpInterceptorFn =
  (req, next) => {

    const token = localStorage.getItem('accessToken');

    if (token) {

      req = req.clone({ setHeaders: { Authorization: `Bearer ${token}` } });
    }

    return next(req);
  };
```

Now:

```text
Browser
   ↓
HttpClient
   ↓
Interceptor
   ↓
JWT added
   ↓
ASP.NET Core API
```

 

# 6. Route Guard

Suppose somebody manually enters:

```text
/customer/dashboard
```

without logging in.

We don't want the dashboard to open.

```typescript
export const authGuard: CanActivateFn = () => {

  const token = localStorage.getItem('accessToken');
  return !!token;
};
```

Routes:

```typescript
export const routes: Routes = 
[
  { path: 'login', component: LoginComponent },

  { path: 'customer',canActivate: [authGuard], children: [
                                                            {path: 'dashboard',component: DashboardComponent},
                                                            {path: 'products', component: ProductsComponent },
                                                            {path: 'proposals', component: ProposalsComponent},
                                                            {path: 'policies', component: PoliciesComponent}
                                                        ]}
];
```

 
# 7. Important Security Lesson

Tell the students: **"Route Guard is UX security. Backend authorization is actual security."** A  malicious user can bypass Angular.

Therefore:

```text
Angular Guard
     ↓
Good user experience

ASP.NET Authorization
     ↓
Actual security
```

Both are necessary.

# 9. Why Create a Dashboard API?

A beginner might call:

```text
GET /customers/me
GET /policies
GET /proposals
GET /premiums
GET /claims
```

and combine everything in the browser. That can work. But a dashboard is a **business-oriented read model**. Instead:

```text
GET /api/customer/dashboard
```

can return exactly what the dashboard needs. This is where the students start seeing the value of:

> **CQRS and read models.**

# 12. Premium Calculation

Now comes an interesting design question. Should Angular calculate the premium? My answer as a mentor:  **Never make the browser the source of truth for financial calculations.**  The frontend may show an estimate. But the authoritative calculation should happen on the server.

```http
POST /api/premium-calculations
```

Request:

```json
{
  "productId": 1,
  "customerId": 1001,
  "sumAssured": 1000000,
  "policyTerm": 20,
  "premiumFrequency": "Yearly"
}
```

Response:

```json
{
  "premiumAmount": 18500,
  "frequency": "Yearly",
  "currency": "INR"
}
```

 
# 13. Why Server-Side Calculation?

Imagine a developer changes JavaScript:

```javascript
premium = 100;
```

Would LIC accept the customer's manipulated premium? Of course not. The authoritative business calculation belongs on the server.This is a general principle:  **Client validates for usability. Server validates for correctness.**

# 20. State Machine

Now teach students something important. Proposal status:

```text
Draft
  ↓
Submitted
  ↓
UnderReview
  ↓
Approved
  ↓
PolicyIssued
```

Alternative:

```text
Submitted
   ↓
Rejected
```

We should not allow:

```text
Draft → Approved ❌
Rejected → Approved ❌
PolicyIssued → Draft ❌
```

This is a **state machine**.

```text
             ┌───────────────┐
             │               ↓
Draft → Submitted → UnderReview → Approved
                    │             │
                    ↓             ↓
                 Rejected     PolicyIssued
```

This is domain modeling.

 
# 21. Why This Matters

Without state rules, developers eventually write code like:

```csharp
proposal.Status = "Approved";
```

anywhere.

Then six months later:

```text
Draft
  ↓
Approved
  ↓
Rejected
  ↓
PolicyIssued
  ↓
Draft
```

The system becomes inconsistent. A domain model should control legal transitions.
